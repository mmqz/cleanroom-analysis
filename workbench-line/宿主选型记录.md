# 阶段 1 宿主选型记录（原型对照后定谳）

> **性质**：《文档工作台完整实施计划》§四.5 的收口交付物。裁决方式 =
> 阶段 1 基准 + 双原型对照后定谳（前端不再无限期悬置）。本记录含
> 可复现命令、实测数字、七维评估与明确主宿主结论。
> **时点**：2026-10-22（mdcore `82884cc` 后）。

## 1. 结论（先行）

**主宿主 = 候选 A：web 技术面（`mdcore/web` CM6 桥 + wasm 核）配
wry/tao 桌面壳（shell-native 蓝图，ADR-H1 既定方向）。**

原生候选 B（egui）保留为可运行的参考实现与降级路径，不作为主宿主。

核心理由（按权重）：

1. **成熟编辑组件复用**：计划阶段 5 明文「正文：继续使用现有成熟的
   Markdown 编辑实现」——即 CM6 桥（W1-W11 冒烟 15/15 + IME CDP
   28/28 全绿，渐进打开 1MB 文档 TTI 153ms 在案）。egui 无对等
   Markdown 编辑组件，从零建设的成本与 IME/选区风险均为实打实的
   工程量（本轮原型正文面板即已暴露：TextEdit 非虚拟化，需自建
   窗口化渲染）。
2. **四类负载实测全部落在 60Hz 帧预算内**（Chromium headless 软件渲染
   环境下）：正文/表格/画布的持续交互帧间隔 16.6ms（vsync 锁定）。
3. **IME 证据**：web 侧真实浏览器输入法通道（CDP imeSetComposition）
   28 检查全过——组合流逐预编辑落核 op、1s 合并窗收单 undo 条、
   跨行提交走兜底同步。egui/winit IME 在位但本轮未验证（环境无
   IME 框架，Xvfb）。
4. **既有资产与测试基建**：web/ 已有 CM6 桥 + xlsx/docx 导入导出面 +
   IME/堆/契约探针；原生侧一切从头。

B 的实测优势（如实记录，构成保留价值）：单进程内存 188MB（A 进程树
673MB）、启动 119-141ms（A 255-277ms）、纯计算命中 0.74µs（A JS
32-53µs，43-70× 差）、单二进制零系统依赖矩阵。若未来目标平台
webview 不可接受（如 Win7 单列目标），B 路径已被证明可运行。

## 2. 方法

- **共享数据集单一真源**（`proto-native --gen`，确定性 LCG，双侧字节
  同源）：10k 块中文正文（2952KB）/ 100 条证据主张 / 500k 格表格
  （5441KB）/ 1k 节点+1.5k 边画布（105KB）。
- **同场景同序**：13 场景（startup/doc_open/doc_edit/doc_jump_end/
  evidence_render/evidence_jump/table_open/table_scroll/table_edit/
  canvas_render/canvas_drag/canvas_hit/fps_sustain），触发-渲染-结算
  口径对称（settle = 触发帧+2 帧 vs 2×rAF；拖拽 = XTEST 真实 X 事件
  vs CDP 真实鼠标；命中 = 双侧应用级 O(n) 同 LCG 点列——命中数
  23=23 互证）。
- **架构纪律双侧同守**：核 = 唯一权威正文（A 经 wasm `apply_ops`，
  B 经 mdcore path 依赖直连）；编辑均回核并验证（revision 递增 +
  文本包含编辑符，双侧全过）。
- **复现命令**：
  - 数据集：`cargo run -p proto-native -- --gen workbench-line/proto-host/data`（proto-native 目录内）
  - A：`python3 workbench-line/proto-host/bench_web.py`（需先 `mdcore/web: build-wasm.sh + npm run build`）
  - B：`cargo build --release && python3 workbench-line/proto-host/bench_native.py`（需 Xvfb :99）
  - 结果：`workbench-line/proto-host/results/{web,native}.json`（双轮稳定性件 web_run2/native_run2）

| evidence_render（100 条） | 30.6 | 31.1 | 12.4 | 11.8 | |

| table_open（500k 格） | 32.7 | 30.8 | 37.6 | 37.1 | 可视窗首渲 |

| canvas_drag（60 步真实输入） | 2148.2 | 2165.1 | 1286.6 | 1280.9 | 位移 (37,21) 双侧 ✓ |

**帧间隔（均值）**：

| 负载 | web | 原生 |
|---|---:|---:|
| table_scroll 滚动帧 | 16.6ms（vsync 锁） | 31.6ms |
| canvas_drag 拖拽帧 | 16.8ms（vsync 锁） | 21.0ms |
| fps_sustain 持续帧 | 16.6ms（vsync 锁） | 20.6ms |

**内存**：web = JS heap 61MB / 浏览器进程树 RSS 673MB；原生 = 单进程
RSS 188MB（HWM 196MB）。

口径注记：
- startup：web = 页面装载→数据 fetch+解析+wasm 摄入+首屏（数据经
  本地 HTTP 171ms）；原生 = 进程起→文件读+serde 解析+核摄入+CJK
  字体装载+首帧。两侧含数据获取路径差异，非纯同构（如实记录）。
- settle 型指标的「ms」含结算帧地板：web ≈ 2×rAF（vsync 16.6ms，
  实际 op 成本多被遮蔽在下限之下）；原生 ≈ 触发帧+2 帧（帧成本
  随 tab 5-33ms）。**单场景绝对值不作跨侧精确比较**，帧间隔行与
  预算结论才是主要判据。
- 帧间隔语义差异：web headless Chromium rAF 被 vsync 锁 16.6ms
  （=「工作在预算内」上界证据，超预算会涨）；原生无 vsync（Xvfb
  GL 交换即时）= 真实软件渲染成本。
- canvas_drag 总时长差（2.1s vs 1.3s）：XTEST 注入间隔 16ms/步 vs
  CDP 驱动器节奏——总时长不可比，帧间隔可比。

## 4. 七维评估（计划 §四.5 逐项）

| 维度 | 候选 A（web+wry） | 候选 B（egui 原生） | 判定 |
|---|---|---|---|
| 渲染表现与交互延迟 | 四类负载全落 60Hz 预算（软渲染环境）；CM6 虚拟化成熟 | 表格帧 31.6ms 超预算（llvmpipe 软渲染；真 GPU 会显著改善）；画布 21ms | A（本环境）；B 需 GPU 复测 |
| 资源占用与启动 | 进程树 673MB；启动 255-277ms | 188MB；119-141ms | **B** |
| 输入法/选区/无障碍/复杂交互 | IME CDP 28/28（真实通道）；CM6 选区成熟；Chromium 无障碍树成熟；复杂文本交互（undo 光标原子跳等）在案 | egui/winit IME 在位未验证；AccessKit 集成在位未启用实测；选区/复杂交互需自建 | **A**（证据落差显著） |
| 目标桌面平台一致性 | webview 矩阵三引擎（Linux webkit2gtk / Win WebView2 / mac WKWebView）——平台间引擎差异是长期税 | 同一渲染器全平台一致 | **B** |
| 现有组件与核心复用 | CM6 桥 + wasm 核面全在（含 xlsx/docx 面）；dist/ 即壳加载物（R10） | 核 path 依赖直连已证；UI 组件从零 | **A** |
| 开发/测试/打包/维护 | web 面测试基建全在；打包 = 三平台 webview 依赖矩阵；npm+Rust 双工具链 | 单二进制打包最简；纯 Rust 单工具链；UI 层开发量大 | 混合（A 开发快、B 打包简） |
| 许可证与发布 | CM6 MIT；webkit2gtk LGPL（动态链接合规）；WebView2 系统组件 | egui MIT/Apache-2.0；winit MIT/Apache-2.0；零传染依赖 | **B**（简明） |

四维 A、两维 B、一维混合 → 主宿主 A；B 的优势维度（内存/启动/打包/
许可/平台一致）构成明确的保留价值与降级触发条件。

## 5. 未测量面（诚实边界——不得写成已达成）

1. **wry/webkit2gtk 桌面壳的编译与运行**：沙箱无 webkit2gtk-4.1/
   GTK3 系统库且无 root 不可装——A 侧测的是 Chromium headless 引擎。
   webkit2gtk 与 Chromium 的渲染差异未测。真机验证 = 阶段 5 前置项
   （在具系统依赖的机器上 `cargo check -p mdshell-native` + 实跑）。
2. **GPU 硬件渲染**：双侧皆软件渲染环境（headless Chromium 软光栅 /
   Xvfb llvmpipe）。原生侧真 GPU 帧成本会显著改善；本记录的 B 帧数据
   是保守上界。
3. **egui IME/无障碍实测**：环境无 IME 框架，未验证。
4. **Win7 单列目标**（计划 §四.5 末段）：WebView2 不支持 Win7——该
   目标若启动，B 路径或旧 webkit 为候选，另行专项。
5. Chromium headless 的 vsync 锁使 web 帧成本只得上界（≤16.6ms），
   精确帧成本未测（不影响预算结论）。
