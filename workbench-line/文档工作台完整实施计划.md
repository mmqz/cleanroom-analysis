# 文档工作台后续完整实施计划

> **性质**：用户 governing 指令原文落档（2026-10-22 IM 通道下达，逐字
> 保留）。本计划取代此前「前端⑤=用户裁决门控」的悬置状态——裁决方式
> 升级为「阶段 1 基准 + 双原型对照后定谳」，前端不再无限期悬置。
> **执行纪律**：每阶段先定验收标准再实施；已完成且有可复现证据的成果
> 直接复用；不重审全部模块；常规细节自主处理，仅不可逆迁移/公开 API
> 重大变更/安全风险/无方案可行时汇总上报。

## 一、总目标

在现有 Rust Headless Core、MD/PDF/Office 引擎、证据系统和命令接口基础上，完成一套真正可运行的 AI + Human 文档工作台。

最终交付必须具备：

1. 人类通过界面、AI 通过命令，共同操作同一份文档及同一张画布。
2. MD、Office、PDF、Canvas 保留各自的领域模型和适合自身的渲染方式。
3. 证据溯源、版本管理、权限、审计及命令校验跨引擎复用。
4. 长文档、大表格、PDF 和 Canvas 各自具备可验证的性能与资源控制。
5. 前端与桌面宿主经过实际工作负载验证后确定，不预先锁定某一种 UI 框架。
6. 核心状态、业务语义和权限规则不依赖 UI、渲染器或桌面宿主。
7. 从测试原型推进到端到端产品，不以单元测试通过、设计文档完成或探针全绿冒充产品交付。

## 二、硬性架构约束

### 1. 三层职责

**领域核心：** 负责文档结构与语义、计算、版本、证据、权限、审计、命令执行和必要的协作状态。

**布局与渲染：** 按表面选择成熟编辑器、分页预览、虚拟网格或专用图形渲染器，各自可替换，不强行统一。

**界面合成：** 负责窗口、面板、输入、选区、滚动、临时交互状态、标注叠加及命令反馈。

必须遵守：

- 核心状态统一，不代表布局引擎统一。
- UI 可以持有选区、滚动位置、临时编辑草稿和拖动预览。
- UI 不得维护第二份权威正文、表格数据或证据库。
- UI 的临时状态必须有明确的提交、取消及失效规则。
- 核心不依赖 GUI 类型、生命周期或具体渲染器。
- 不默认所有功能独立进程，也不默认采用共享内存或 GPU 纹理协议。
- 高风险 Office 转换继续采用受控子进程；其他进程隔离需求由实测和可靠性要求决定。

### 2. 统一命令与事件

命令层只提供必要的公共契约，不做万能工作流框架。

每个写操作应明确：
- 命令 ID、操作者和目标对象。
- 幂等键与预期版本。
- 参数与权限校验。
- 成功后的版本变化。
- 失败、冲突、重试和取消语义。
- 可审计的操作结果与相关事件。

拖动、输入和批量修改不能绕开核心校验，直接修改另一份数据副本。高频交互可以在界面本地预览，再按明确策略提交或同步。

## 三、阶段 0：当前成果收口

先完成当前尚未收口的事项，再开始新功能。

1. 使用最新 HANDOFF 恢复真实状态，确认双仓提交、分支、工作区及现有测试结果。不重新开展全仓审计。
2. 验证 JSON sidecar 的原子写入、损坏检测、异常退出恢复、版本兼容及正文和证据版本一致性。
3. 运行 mdc-workbench 八步闭环和必要的相关门禁。
4. 核实 Office 锚点的真实合并状态、已知 yrs 缺陷处理状态，以及协作和 Canvas 目前究竟是原型还是产品实现。
5. 更新 HANDOFF，明确区分已实现、已验证、部分集成、延期和未实施。

如果上述事项已有完整且可复现的证据，可以直接复用，不重复无关检查。

**验收：** 现有成果可复现，重要缺陷有明确处置结论，交接文档与实际仓库一致。

## 四、阶段 1：性能基线和前端宿主选型

先以现有引擎能力建立三类基准，并在有可运行 Canvas 原型时加入第四类。

### 1. 长文档与证据侧栏

测量：
- 输入到界面更新的延迟。
- 长文档滚动和分页切换表现。
- 正文定位到来源及高亮的延迟。
- 证据侧栏更新是否导致正文重排。
- CPU、内存、失败及恢复行为。

### 2. 大表格

测量：
- 行列切片读取及提交延迟。
- 滚动和可视区更新表现。
- 选区、编辑、复制粘贴、键盘导航。
- 公式计算和证据高亮的局部更新。
- 数据规模上升时的内存和响应时间。

先实现版本化切片、可视区虚拟化、局部更新和浮层单元格编辑。只有测量表明不足时，再投入自绘网格、Canvas 或 WebGL。

### 3. PDF

测量：
- 首屏及后续页面渲染延迟。
- 连续滚动、缩放、缓存命中表现。
- 文字选择、批注及证据区域高亮。
- 缓存内存、异常渲染、超时和恢复。

继续复用现有 PDFium 渲染能力，不建立第二套 PDF 解析真相。先完成页面缓存和稳定滚动，不提前引入共享纹理。

### 4. Canvas 原型

若已有原型，直接测量；若没有，建立最小节点与连线场景。

测量拖动、缩放、命中检测、批量修改和 AI 命令更新的响应时间、帧表现及内存。节点数量采用基准数据集与压力数据集分开记录，不预先承诺未经测试的帧率。

### 5. 前端与宿主选型

先查看已有代码和可以复用的前端能力。若没有合适的宿主，最多实现两种具有代表性的最小原型：

- 一种基于 Web 技术的桌面候选。
- 一种基于原生 UI 或原生渲染的候选。

具体候选按现有代码、组件生态、许可和维护成本选择。Slint 不因 Kokoa 兼容而成为默认主 UI。Qt Quick、React/WebView 等均可作为候选，但不因品牌或宣传直接胜出。

使用相同的正文、证据侧栏、表格和 Canvas 操作进行对照，综合评估：
- 渲染表现与实际交互延迟。
- 资源占用与应用启动。
- 输入法、文本选择、无障碍和复杂交互支持。
- 目标桌面平台一致性。
- 现有编辑组件和 Rust 核心的复用程度。
- 开发、测试、打包及长期维护成本。
- 许可证与发布约束。

最终形成一份简明选型记录并确定主宿主。不要将不同层面的跑分混为同一性能结论。Windows 7 作为单独的兼容目标，不阻塞现代主平台选型，也不允许通过停止维护的运行时冒充正式支持。

**验收：** 有可复现的性能基线、候选比较结果、明确的宿主选型及理由。不得把未经测量的指标写成已经达成的承诺。

## 五、阶段 2：稳固证据与命令基础

在现有证据 MVP 上增量完善，不重新设计已经落地的核心。

1. 验证 XLSX 来源定位、DOCX 正文映射、计算输入、公式和结果的完整关联。
2. 验证文档或原材料版本变化时，失效关联能够被识别。
3. 来源指纹或定位不匹配时，不得自动恢复为已核验。
4. 计算复算、来源关联和人工审核状态分开表示。
5. 验证导出正文与 sidecar 可独立使用。
6. 验证 sidecar 丢失、损坏及正文被外部编辑后的处理。
7. 将现有命令、版本检查、幂等、审计和权限作为后续 UI 的统一入口。

证据系统是横向能力，不是标书专用模块。使用合成样例完成自动化验证，并保留不同业务场景可配置的审核门槛。

**验收：** 现有证据闭环可复现；UI 接入不需要建立第二份权威数据；失效和失败状态能够被明确表达。

## 六、阶段 3：协作引擎完成实施

在已存在的 yrs 适配器和探针基础上，将协作能力从实验验证推进到真实文档操作。

### 1. 先解决已知正确性问题

- 复现双 UndoManager、非零捕获窗、交错 origin 导致部分撤销及 redo panic 的路径。
- 验证捕获窗改为 0 的缓解方案。
- 检查普通输入的撤销粒度，避免每个字符都形成不合理的撤销操作。
- 明确事务边界和写锁释放规则。
- 验证对象删除、恢复、锚点变化、保存和重新打开后的行为。

已知缺陷的触发条件消失，不等于所有 undo/redo 路径安全。保留最小复现和修复前后回归。

### 2. 解决历史与内存边界

调查当前 yrs 版本支持的撤销栈逐出、截断和资源控制能力，测量典型工作负载及压力场景。

不得伪造一个实际上无法强制执行的内存上限，也不得在栈达到阈值时静默清空全部撤销历史。

若现有 API 无法安全实现预期策略，应明确记录剩余限制，并实现经过验证的降级或拒绝策略。任何改变用户可见撤销语义的选择都必须说明其影响，不得假称已经完整解决。

### 3. 接入真正的编辑操作

实现：
- 稳定逻辑 ID 与 CRDT ID 的分离。
- 人类与 AI 写操作使用同一命令契约。
- 版本变化和状态事件通知。
- 并发编辑、冲突和过期命令处理。
- 保存、断连、恢复、删除及复原的完整路径。
- 会话本地撤销等已确定的产品语义。
- 真实编辑器与协作状态的集成测试。

保持按引擎或文档边界组织协作状态，不将 MD、Office、PDF 和 Canvas 强制变成同一个 CRDT 文档。

**验收：** 至少有一个真实可运行的协作文档场景，而不是只有独立适配器测试。人类修改后 AI 能读取最新版本，AI 修改后人类能看到结果；交错操作、撤销重做及恢复场景都有可重复的验证。

## 七、阶段 4：Canvas 引擎

协作基础可用后，独立实施 Canvas 领域模型和真实交互。不得只完成数据结构或渲染演示就宣布 Canvas 完工。

### 1. 独立数据模型

第一版支持：
- 稳定对象 ID。
- 节点、连线、位置、尺寸及基础分组。
- 节点属性与内容。
- 选择、创建、移动、连接、删除及复原。
- 明确的对象版本和冲突处理规则。
- 必要时将节点或关系关联到证据记录。

根据真实用例增加图层、吸附、布局和其他功能。不要一开始建设万能图形编辑器。

### 2. 统一操作入口

人类通过 UI 选择、拖动和编辑；AI 通过同一命令接口创建节点、修改属性、连接对象和组织布局。

双方必须修改同一份画布权威状态，而不是分别维护两个副本。需要冲突处理时，要明确相同属性被同时修改的结果，不能仅依赖 CRDT 自动合并就认定业务正确。

对拖动预览和提交操作进行区分，避免每个像素变化都无限增加撤销记录；同步频率及操作分组根据实际交互测试确定。

### 3. 渲染按实测决定

第一版使用能满足功能的简单渲染方式；根据节点规模、交互延迟和内存确定是否需要更专用的图形引擎。

不预先锁定 Vello、wgpu、Skia、WebGL、GPU 纹理或独立进程。只有对照测试证明现有方案不满足目标时，才更换渲染路径。

### 4. 协同与证据集成

验证人类拖动节点时 AI 能读取当前状态并执行操作；AI 修改后 UI 能正确更新；双方对同一节点产生冲突时遵循明确规则。

节点和连线可以关联证据；来源或证据状态变化后，画布上的对应提示能够更新，但证据存储仍独立于 Canvas 模型。

**验收：** 有可运行的节点连线画布，有真实 AI 命令操作，有并发修改、撤销、复原、证据关联及压力测试，不只是静态效果展示。

## 八、阶段 5：完成各个渲染表面

按照阶段 1 确定的宿主及基准结果实施，不重造已成熟的组件。

### 1. 壳与证据界面
完成工程树、证据侧栏、审核报告、命令进度和状态提示。大量列表使用虚拟化，写入统一经命令接口。

### 2. 正文
继续使用现有成熟的 Markdown 编辑实现，支持选区、输入法、增量更新与证据定位。DOCX 预览按需选择现有排版能力或分页方案，不将整篇复杂文档塞进单一 DOM，也不强行让核心输出所有文字位图。

### 3. 表格
完成切片、虚拟滚动、局部更新、冻结区域、单元格编辑、复制粘贴、键盘导航、计算结果和证据高亮。若现有技术无法达到基线，再引入自绘网格或 GPU 技术。

### 4. PDF
完成页面缓存、缩放和滚动、文字选区、批注及证据区域叠加。优先复用 PDFium 和既有安全边界。

### 5. Canvas
完成实际节点编辑与协同操作，再根据性能结果决定是否替换渲染器。

**验收：** 四类表面均有可重复的交互测试及性能数据；不存在因局部更新而覆盖核心新版本的错误，也不存在 UI 第二权威状态。

## 九、阶段 6：端到端质量与发布

建立能从实际使用路径验证完整工作台的测试集合。

至少覆盖：

1. 长文档编辑、定位及来源跳转。
2. XLSX 切片读取、单元格编辑、计算和证据更新。
3. PDF 连续滚动、缩放、批注及证据高亮。
4. 人类和 AI 对同一文档与画布的操作。
5. 并发修改、过期命令、撤销重做、删除与复原。
6. sidecar 丢失、损坏、版本不匹配及异常退出。
7. 超大或异常输入、超时和资源耗尽。
8. 应用退出、重启、断连和恢复。
9. 目标平台的打包、输入法、字体、交互和渲染一致性。
10. Kokoa/Slint 的可选适配通过独立接口验证，不要求核心依赖该宿主。

完成安全与资源限制核查、依赖许可证清单、安装与升级测试，以及必要的性能回归。只有实际完成的项目才能标记通过，不以理论设计替代端到端验证。

## 十、执行纪律与停止条件

1. 下一轮从最新 HANDOFF 和仓库真实状态开始，局部核实后直接实施，不反复重审所有模块。
2. 先完成当前收尾，再依次进行性能基线、宿主选型、协作实施、Canvas 实施、渲染表面集成及端到端验收。
3. 每个阶段先确定验收标准，再实现、测试、检查差异、修复真实缺陷、提交并推送。
4. 对已经完成并有可重复证据的成果复用既有验证；新增测试只覆盖必要路径和受到影响的模块。
5. 保留进度记录、决策理由、测试命令、实际结果、提交号和剩余风险。
6. 不为了追求性能提前引入多进程、共享内存、GPU 渲染器或第二套编辑器。
7. 不为兼容 Kokoa 而默认使用 Slint；不因前端选型让核心依赖任何 UI。
8. 不声称未实测的性能指标已达成，不以原型、探针或单元测试代替完整产品验证。
9. 常规实现细节自主处理，不逐轮等待审批。仅在涉及无法逆转的数据迁移、公开 API 重大变化、不可接受的安全风险或尚无可行实现方案时，才汇总具体阻塞及推荐选项。
10. 所有阶段的验收条件满足、代码及必要的集成成果已提交推送、文档与实际状态一致后，才报告整体完成。

最终交付标准是：**一个真实可用的工作台；核心状态与命令可信；文档、表格、PDF 和 Canvas 各自拥有适合的渲染路径；人类和 AI 能在共同状态上工作；性能和恢复行为有实测证据。**
