# 06 · 逐节深度解析（下）：§13–§23 与 Final Rule

> 接上半篇。上半篇见 `06-逐节深度解析-上.md`。

---

## §13 Rust Rules（行 384-423）

- **意图**：Rust 代码必须"刻意地"使用其安全模型，而非仪式性地。
- **机制**：`unsafe` 不自动禁止，但引入前必须过 5 项检查（有无安全替代→边界能否更小→项目是否已有成熟 unsafe 抽象→是否为 FFI/OS集成/性能的具体刚需→安全不变量能否陈述并维护）；优先形态是"小 unsafe 边界→安全抽象→普通安全代码"；重写章节要求先理解所有权/生命周期/并发/资源管理/错误语义/FFI 边界/性能特征，再做惯用式实现。
- **深析**：这是全文唯一的技术栈专属章节，103 词的 unsafe 小节否定密度 29.1‰（3 条 Do not：不扩散 unsafe / 不为图省事引入 unsafe / 不给普通代码加装饰性注释）。"安全不变量必须写在边界附近"是 Rust 社区最佳实践（rust-lang unsafe-code-guidelines 精神）的浓缩。RUST_REWRITE 在 §5 独立成类 + 本章存在，共同暗示作者的 Rust 重写工作流背景。

## §14 Avoid Overengineering（行 424-445）

- **意图**：最小架构满足真实需求。
- **机制**：7 类禁加抽象清单（managers/factories/generic traits/wrappers/configuration layers/state machines/frameworks）+ "每个重要抽象必须有存在的具体理由"。
- **深析**：40.8‰ 否定密度全文档第二高。这份清单与 Overengineering 检测工具（如 Sonar、enry 的抽象密度指标）关注的模式完全一致。"理论可复用"不构成理由——只有"仓库实际需求"构成理由，这是对 LLM 过度泛化倾向（训练数据中大量演示性抽象）的直接矫正。

## §15 Avoid Over-Safety and Over-Commenting（行 446-463）

- **意图**：反过度防御、反废话注释。
- **机制**：安全上"识别真实威胁，用最小有效缓解，然后验证"；注释上只解释五类内容（非显然选择的原因/协议或外部约束/变通方案/安全不变量/微妙算法不变量），"不叙述显然的代码"。
- **深析**：38.5‰ 否定密度。本章与 §14 构成"反过度"双子章——一个管结构过度，一个管行为过度（防御性编程与注释噪音）。有趣的是它同时与 §13 的 unsafe 纪律形成张力平衡：§13 管"安全不足"，§15 管"安全过剩"——作者的立场是**安全投入要对应真实威胁模型**，既不缺位也不撒胡椒面。这本身就是一个成熟安全观的样本。

## §16 Debugging（行 464-482）

- **意图**：禁止"随机改动多个不相关的东西"来应对失败测试。
- **机制**：六步调试协议：Observe → Reproduce → Isolate → Hypothesis → Minimal change → Verify。
- **深析**：这是经典科学方法（观察→复现→隔离→假设→最小变更→验证）在调试领域的直接移植，34 词的极简表述。"Keep useful failure evidence in durable project state" 把跨会话仍会踩的坑固化到持久记忆（与 §2 的 9 类必落盘事实中 "known failures and their causes" 呼应）——失败的复利利用。

## §17 Verification Is Part of Implementation（行 483-525）

- **意图**：验证是实现的一部分，不是事后步骤。
- **机制**：7 级验证流水线（静态检查→单元→集成→构建→真实进程/服务执行→真实用户路径→回归），取"可用的最强实践级"；5 组反直觉等式（cargo check ≠ 可工作的 Rust 程序 / build ≠ 可工作的前端 / HTTP 200 ≠ 正确的 API 行为 / 页面渲染了 ≠ 可工作的应用 / 按钮可见 ≠ 功能已实现）；分域验证策略（前端→浏览器渲染、运行时/CLI→执行真实二进制、API→打真实端点、持久化→CRUD+重启验证状态存活）。
- **深析**：114 词的长节，**零否定式**（0‰）——因为它全是正面清单，是全文最"程序化"的一章。5 组等式全部针对"把中间产物当最终结果"的验证作弊。`[NOT VERIFIED] reason: ...` 是一个强制的**诚实性输出协议**：做不到真验证时必须在报告里打标——与 §23 报告模板的 `[NOT VERIFIED]` 字段首尾呼应。

## §18 Independent Review（行 526-555）

- **意图**：有意义的变更完成后必须独立审查。
- **机制**：派生条件（大重构/Rust unsafe与FFI/安全敏感代码/架构变更/前端重设计/迁移/跨多模块变更——7 类场景建议用子代理）；审查者检查 9 类缺陷（缺失需求/假或降级实现/回归/不必要复杂度/unsafe 假设/错误处理不当/耦合/文档漂移/UI 与实际行为不匹配）；修复有意义的发现后重跑相关验证。
- **深析**：71 词，零否定式。这是**角色分离**（实现者 ≠ 审查者）在单代理环境下的实现——子代理不带实现者的沉没成本与自我辩护偏差。9 项检查清单与 §8/§9（假实现）、§14（复杂度）、§19（文档漂移）、§7（UI行为）逐项咬合，说明清单不是泛泛而谈而是对前文的系统性收网。

## §19 Documentation as an Executable Contract（行 556-577）

- **意图**：描述行为的文档必须与实现保持一致——文档是契约不是纪念品。
- **机制**：触发清单（改命令/API/架构/配置/用户工作流/支持平台/安装说明→同阶段更新对应持久文档）；两条硬规则：不创建第二份竞争"真相"、重大决策优先写小的决策记录而非改写大的历史文档。
- **深析**："Do not create a second document containing a competing 'truth'" 直指文档治理的经典死穴（多份文档各自为政）。"小决策记录优于改写大历史文档" 是 ADR（Architecture Decision Records）实践的标准姿态。与 §3（真相仲裁）构成双向闭环：§3 管冲突发生时，§19 管冲突的产生预防。

## §20 Git Safety and Delivery（行 578-605）

- **意图**：Git 操作三阶段安全程序。
- **机制**：修改前（`git status` / `git branch --show-current` / `git remote -v`——先看清自己在哪、在什么分支、远程是谁）→ 保护无关用户变更 → 实现后（`git diff --stat` / `git diff` / `git status`）→ 只提交相关工作 → 需要远程同步时验证后 push → "Never claim a push succeeded without actual evidence"。
- **深析**：全文档唯一包含真实 shell 命令的一节，6 条命令全部只读——设计上把**可变更操作（commit/push）留在语义层、检查操作放在字面层**，字面命令永远安全。47 词紧凑节，反欺骗条款是本章的签名。"Push: SUCCESS / FAILED" 进入 §23 报告模板的固定字段，push 状态必须可查证。

## §21 Durable Phase State（行 606-629）

- **意图**：多阶段工作维护紧凑的持久状态文件。
- **机制**：状态文件（WORKLOG.md/TASKS.md）只允许 7 类内容（当前阶段/已完成的已验证工作/已知失败/未解阻塞/重要决策/下一阶段/验证证据）；阶段完成时**提交前**更新此状态；理由明示："执行环境可能无警告重置"。
- **深析**："不写按时间顺序的转录"（Do not write a chronological transcript）与 §2 的"不写日记"双保险。"提交前更新"的顺序设计很精妙：状态文件永远先于代码变更入库，即使 push 前环境死亡，恢复者拿到的提交里永远带着最新阶段状态——**把状态文件当作检查点（checkpoint）**。

## §22 Completion Gate（行 630-653）

- **意图**：宣布阶段完成前的最后一道闸。
- **机制**：13 项检查清单（目标实现/无故意降级或假实现/技能已发现使用或明确不需要/既有架构已理解/范围已遵守/测试已跑/真实行为已尽可能验证/已按需独立审查/重要文档一致/持久阶段状态已更新/Git 状态已理解/仓库工作完成时已提交/需要时远程已同步）。
- **深析**：68 词，零否定式（纯检查表），但收尾句 "A checked box without evidence is not evidence" 是全文最锋利的反欺骗条款之一——直接否定了"勾选框即完成"的代理自证模式。13 项与 §1 的 13 步管线首尾呼应（每步管线对应一项闸门），结构上是**镜像设计**。

## §23 Final Report（行 654-687）

- **意图**：固定模板的最终报告。
- **机制**：7 节模板（Result/Changes/Skills/Verification[带 PASS 与 NOT VERIFIED 标记]/Review/Git[Branch/Commit/Push: SUCCESS|FAILED]/Status[COMPLETED|PARTIALLY VERIFIED|NOT VERIFIED|FAILED]）。
- **深析**：模板把 §12 的证据等级（OBSERVED/INFERRED/UNKNOWN）、§17 的 [NOT VERIFIED] 标注、§20 的 push 证据全部**物化为固定字段**——报告结构本身强制诚实。"Do not claim success from intention, compilation, screenshots, or plausible reasoning alone" 点名四种最常见的成功幻觉来源。

## Final Rule（行 689-707）

- **意图**：全文档的收束与重申。
- **机制**：7 条加粗律令（仓库能给出的事实就不靠记忆 / 任务要可工作系统时不停在壳上 / 不静默降级实现 / 不写计划代替干活 / 计划好一个连贯阶段就端到端执行并验证 / 上下文可能消失就把重要状态写进仓库 / 先用技能与既有项目知识再发明自己的工作流）+ 终极目标句："目标不是看起来像个胜任的开发者，而是把仓库留在**另一个代理可以检查、运行、验证、继续**的状态——不需要上一次对话。"
- **深析**：108 词、4 条否定、37‰ 否定密度、7 条全部加粗——这是利用 LLM **近因效应（recency bias）**的尾部重锚：宪法主体读完后，最后 19 行重新压缩全部核心约束。终极目标句是整份文件的"设计验收标准"：可交接性（另一个代理可无缝接管）优先于表现（看起来胜任）——这与 Purpose 段的"真实工程 vs 貌似合理"对立轴首尾闭环。

## 全文档的三个结构韵律（总结）

1. **管线镜像**：§1 的 13 步执行管线 ↔ §22 的 13 项完成闸 ↔ §23 的 7 节报告——同一流程的三种投影（过程视图/门视图/交付视图）。
2. **双章定则**：大原则全部拆成两章执行——§8 定义+§9 禁止（假实现）、§14 结构+§15 行为（反过度）、§3 检测+§19 预防（文档一致性）、§2 读取+§21 写入（持久状态）。
3. **否定密度曲线**：开头（身份与世界观的绝对禁令 20-29‰）→ 中段（流程章节 0-15‰）→ 反过度双子章峰值（36-41‰）→ 报告与门（0‰ 纯正面清单）→ Final Rule 收尾重锚（37‰）。**否定式的分布本身就是一张注意力地图**——它标出了作者最担心代理出错的位置。
