# 06 · 逐节深度解析（上）：Purpose 与 §1–§12

> 对 25 个结构单元逐一做三层解析：**意图**（这一节想让代理做什么）→ **机制**（它如何改变 LLM 的行为路径）→ **深析**（细节、交叉引用、量化特征）。风险定性已集中于 04 文档，此处只做补充。

---

## Purpose（行 3-10）

- **意图**：设定代理身份——"完成真实工程工作的工程代理，而非产出'看起来合理'的代码"。
- **机制**：身份框架（identity framing）是提示工程中对 LLM 行为影响最强的手段之一；第二段立即引入"会话/模型/沙箱都可能消失，仓库才是持久记忆"的世界观。
- **深析**：49 词里完成了身份 + 世界观 + 记忆模型三重设定。用词刻意区分 "engineering work"（真实工程）与 "plausible code"（貌似合理的代码）——这组对立贯穿全文（§8 无壳、§17 验证、§23 报告），是整部宪法的**核心对立轴**。

## §1 Non-Negotiable Operating Model（行 11-39）

- **意图**：给出唯一的全局执行管线：理解→分类→检查持久上下文→发现技能→研究→比例规划→执行一个完整阶段→验证真实行为→独立审查→修复→再验证→持久化→提交→按需推送。
- **机制**：13 步管线是**认知脚手架**——LLM 对显式序列的遵循率远高于散布的规则；两条"Do not"（不要因为听起来简单就立刻动手 / 不要因为能编译就停下）精准封堵了 coding agent 的两个最高频失败模式（轻率开工、过早收工）。
- **深析**：标题"Non-Negotiable" + 全文唯一加粗句 "Evidence beats assertion. Working behavior beats plausible implementation." 位于章节中心——加粗+居中的组合是注意力权重最高的排版位置。本节 29‰ 的否定密度排在全文档前列。

## §2 Context Is Ephemeral; Repository State Is Durable（行 40-77）

- **意图**：确立状态模型——chat/记忆/沙箱随时消失；仓库是唯一可靠记忆。
- **机制**：给出 8 类记忆文件的**最小发现集**（AGENTS/CLAUDE.md、README、ARCHITECTURE、DECISIONS、WORKLOG、TASKS/PLAN、DESIGN/PAGES），并立即用"不要自动创建全部文件"防止代理的过度文档化倾向（与 §14 反过度工程呼应）。子节 durable-state rule 列出 9 类必须落盘的事实（架构决策、约束、命令、运行时行为、外部集成、失败原因、阶段状态、验证证据、对上游的有意偏离）。
- **深析**："Do not turn durable documents into a diary. Record decisions and facts, not every action"——这句话把状态文件的信噪比问题上升为硬规则，直指 agent 工作日志最常见的退化模式（流水账污染记忆）。本节是对 **无状态计算架构**（serverless）思想的移植：运行时无状态、状态全部外置。

## §3 Source of Truth and Documentation Consistency（行 78-105）

- **意图**：文档冲突时的裁判规则。
- **机制**：6 级真相优先级（运行行为 > 源码配置 > 决策记录 > 任务计划 > README > 陈旧笔记）+ 4 步不一致处理流程（判定哪个是当前的→更新过期文档→不留矛盾指令→记录范围变更决策）。
- **深析**：这是全文唯一的形式化**仲裁器**。妙处在于把"文档漂移"定义为需要主动处理的缺陷而非可忽略的噪音，并与 §19（文档契约）形成"检测→修复"闭环。"Never claim documentation is current without checking it against the implementation" 再次强化反断言纪律。

## §4 Work Resumption Protocol（行 106-123）

- **意图**：新会话/上下文重置后的标准冷启动序列。
- **机制**：7 步（git status → 读指令 → 读持久状态 → 查提交 → 查代码 → **验证实际完成度** → 从已验证状态继续）。
- **深析**：第 6 步是灵魂——"不信任上一次会话声称的完成，用代码/测试/运行时证据验证"。这实质是把 git 仓库当作**可审计的账本**而非聊天记录的延伸。配套两条反模式：不因对话丢失而重做已完成工作、不因清单打了勾就认为完成（后者在 §22 以 "A checked box without evidence is not evidence" 再次收尾）。

## §5 Classify the Work Before Acting（行 124-151）

- **意图**：强制任务先分类再动手。
- **机制**：14 类枚举（IMPLEMENTATION / BUG_FIX / REFACTOR / MIGRATION / RUST_REWRITE / RESEARCH / PRODUCT_ANALYSIS / ARCHITECTURE / FRONTEND / PERFORMANCE / TESTING / DEBUGGING / DOCUMENTATION / RELEASE / OTHER）。
- **深析**：关键句是 "Different work requires different evidence"——分类的目的不是打标签，而是**选择证据标准**（BUG_FIX 要复现证据、DOCUMENTATION 要一致性检查、PERFORMANCE 要基准数据）。"不要用编码工作流做产品分析"直接封堵类型错配。注意 RUST_REWRITE 作为独立类型存在——与 §13 Rust 规则呼应，说明作者预期 Rust 重写是高频任务类别。

## §6 Skills First（行 152-196）

- **意图**：实质性工作前先做技能/插件发现。
- **机制**：两级发现——本地（7 个目录 + 宿主注册表）→ 外部（7 个 GitHub 仓库，仅当本地无合适技能）。技能加载契约 4 步：读 SKILL.md → 按需读引用 → 遵循其验证/交付契约 → 复用其脚本与工作流。
- **深析**：选择策略"最小相关技能优于大而不相关的集合"控制上下文占用（技能膨胀会稀释指令权重）。外部仓库段自带供应链缓解语义（"inspect and adapt only what is relevant; do not blindly install"），但无机制保证——这是全文档**唯一的远程内容入口**（详见 05 文档的实测：当前 7 仓库全部良性，其中 PracticalSwan 自带 skillguard 注入扫描器）。本节否定密度仅 8.7‰——因为在讲"发现与加载"，而非"禁止"。

## §7 Frontend Work Must Be Product-Level（行 197-226）

- **意图**：前端任务必须达到产品级，而非组件级。
- **机制**：7 步工作流（检查现有产品与设计系统→识别主要用户任务→研究最强商业产品→检查真实交互态而非截图→先建立视觉系统再复制组件→实现真实交互与数据流→浏览器渲染验证）。
- **深析**：151 词的长节。两个亮点：①"检查实际交互状态，而非仅截图"——针对 LLM 前端工作最大的作弊空间（截图无法反映断连状态）；②反 AI 模式七连禁（任意紫蓝渐变/无意义玻璃卡片/默认 hero+三卡片/过度圆角/无目的装饰动效/假指标假证言/按钮不做所宣传的事）——这条清单对 2024-2026 年 AI 生成 UI 的统计性审美劣化描述得极其精准，堪称"AI 生成界面的病理切片"。

## §8 No Shell Implementations（行 227-280）

- **意图**：硬性禁止"壳实现"（看起来完整、实际断连的假功能）。全文唯一的 "hard requirement" 表述。
- **机制**：用 6 组对照（UI存在但状态是假的 / 按钮存在但动作未接线 / API客户端存在但从不调用 / 后端存在但前端不消费 / 工作流看似完整但只有硬编码happy-path）定义"不完整"，再用 7 层数据流追踪（用户动作→UI状态→应用逻辑→数据/API/存储→真实结果→错误态→加载/空态→UI更新）定义"完整"。
- **深析**：这 7 层追踪本质是**全链路集成测试的定义**——把"完成"的可判定标准从编译通过提升到状态机遍历。与 §17 的验证流水线形成"定义→检查"闭环。若某层暂时无法实现，必须"陈述确切缺失的依赖并标记不完整"——禁止伪装完成。

## §9 No Degraded Implementation Without Explicit Approval（行 281-300）

- **意图**：禁止静默降级。
- **机制**：11 类降级形态黑名单（mock 数据/静态 HTML/占位 API/假持久化/简化协议/降低并发/假认证/不完整错误处理/硬编码/遮掩未实现内核的门面/要工作实现时交付"概念验证"）。
- **深析**：§8 定义"什么是假"，§9 定义"不许用假的顶替真的"——两章是同一原则的**定义条款与执行条款**。出口条款设计得很克制："如果暂时无法完整实现，停在真实边界并报告"——允许不完成，不允许伪装完成。这与恶意软件的伪装行为（fake progress bar、假成功提示）形成有趣对照：本文件把"伪装完成"列为最高禁忌。

## §10 One-Phase YOLO Execution（行 301-330）

- **意图**：阶段计划确立后整阶段连续执行，不逐步请示。
- **机制**：动机声明（环境"调用廉价但连续性有限"）→ 默认模式（计划→端到端执行→验证→审查→修复→持久化→报告）→ 5 个暂停门（破坏性/不可逆操作、凭据/权限、真阻塞性歧义、范围必须实质变更、继续会危及无关用户工作）。
- **深析**：全文档**唯一放权条款**，也是监督面最敏感的条款。设计上属"批处理自治"：把确认粒度从"每步"提高到"每阶段"，用 5 个语义门守卫不可逆边界。106 词里否定式仅 2 条且都是反摩擦的（不要每小步停下确认、不要把多步阶段变成几十个对话检查点）——注意它没有放弃任何安全语义门。风险不在条款本身，而在宿主 LLM 对"破坏性/不可逆"的判定是概率性的（04 文档已给出宿主层硬机制兜底建议）。

## §11 Proportional Planning（行 331-353）

- **意图**：计划与任务体量成比例。
- **机制**：8 字段计划模板（Goal/Scope/Constraints/Current facts/Unknowns/Approach/Acceptance criteria/Verification）+ "The plan is not the deliverable"。
- **深析**：Unknowns 字段单列是亮点——强迫代理在计划期就暴露认知盲区，而不是在执行期撞上。"验收标准"与"验证方法"分列，前者定义"什么算好"，后者定义"怎么证明好"——这是把 V&V（验证与确认）思想压进了 8 行模板。

## §12 Research Before Reimplementation（行 354-383）

- **意图**：重写/分析现有系统前强制先研究。
- **机制**：8 步研究链（现有实现→行为→架构→约束→测试→上游 issue/PR→已知权衡→目标架构→实现）+ 三级证据词汇表 OBSERVED / INFERRED / UNKNOWN。
- **深析**："Never turn inference into fact" 是全文最短的强条款之一。三级词汇表是一个**认识论约束**——要求代理在输出中显式标注每个断言的证据等级，直接对抗 LLM 的幻觉倾向（把推断说得像事实）。36.4‰ 的否定密度反映其防御性强度。
