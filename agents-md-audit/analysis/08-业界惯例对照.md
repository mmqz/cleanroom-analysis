# 08 · 业界惯例对照：它处在 AGENTS.md 生态的什么位置

> 基准：agents.md 官方规范（agents.md，2026-10-09 实抓）、Claude Code CLAUDE.md 惯例、Cursor rules、Vercel open-agents 实测（本会话克隆验证）。证据分级遵循被审计文件自己的纪律：**OBSERVED**=本会话直接验证；**INFERRED**=合理推断；**UNKNOWN**=未建立。

## 1. 与 agents.md 官方规范的关系

**OBSERVED**（实抓 agents.md 首页）：官方把 AGENTS.md 定位为"README for agents"——一个给 AI 编程代理的、可预测的指令存放点，典型内容是三类：Setup commands（`pnpm install` / `pnpm dev` / `pnpm test`）、Code style（strict mode、引号分号风格、函数式模式）、Testing instructions。官方声明兼容 60k+ 开源项目与 30+ 代理宿主（Codex、Jules、Aider、goose、opencode、Zed、Warp、VS Code、Devin、Cursor、Gemini CLI、GitHub Copilot、Windsurf、Junie 等）。

**对照结论**：

| 维度 | 官方规范建议 | 被审计文件 |
|---|---|---|
| 定位 | 项目说明书（描述性：这个项目怎么构建/测试） | 代理行为法典（规范性：代理必须如何工作） |
| 内容类型 | setup / style / testing | 23 章行为协议（分类、执行、验证、交付） |
| 粒度 | 单项目、几十行 | 跨项目、707 行 |
| 唯一交集 | 结构惯例（标题+列表+代码块）、"文档与实现一致"精神 | — |

二者**互补而非竞争**：官方规范描述"项目的事实"，本文件约束"代理的行为"。实践中典型的部署方式是把本文件放在用户/组织层（如 `~/.claude/CLAUDE.md` 或全局 AGENTS.md），项目层再放官方风格的项目 AGENTS.md——§6 的技能目录清单（`~/.claude/skills/` 与 `.claude/skills/` 并列）证实了这种双层设计意图。

## 2. 与 Claude Code CLAUDE.md 惯例对照

**OBSERVED**：open-agents 仓库中 `CLAUDE.md → AGENTS.md` 软链，证实 Claude Code 与 AGENTS.md 惯例已事实上统一。
**INFERRED**：本文件 §2 的 8 类记忆文件清单（CLAUDE.md/AGENTS.md、ARCHITECTURE.md、WORKLOG.md…）与 Claude Code 社区的记忆分层实践一致；§18 的"sub-agent when available"对应 Claude Code 的 Task/subagent 能力。
**本文件超出惯例的部分**：证据分级词汇表（OBSERVED/INFERRED/UNKNOWN）、[NOT VERIFIED] 输出协议、完成门 13 项、push 证据条款——这些在常见 CLAUDE.md 模板中均不存在，属于作者的增量设计。

## 3. 与 Cursor rules 生态对照

**INFERRED**：Cursor 的 .cursor/rules 采用分散的规则文件+glob 触发模式（按文件路径激活规则）。本文件不做路径触发，改做**语义条件触发**（15 个休眠触发器），覆盖面更广但精度低于按路径激活；代价是无宿主机制支撑时全靠 LLM 判断触发条件。

## 4. 与 Vercel open-agents 实测对照

**OBSERVED**（本会话克隆验证）：open-agents 是三层系统（Web → Agent 工作流 → Sandbox VM），代理**不在**沙箱内运行、通过工具层交互（bash/read/write/glob/grep/skill/task/todo/fetch + path-security 凭据黑名单）。其自带 AGENTS.md 是 131 行项目级指南（认证/数据库迁移/命令/代码风格/git 惯例）。
**交叉验证结论**：被审计文件的 Layer 0 假设（宿主提供工具与沙箱、环境可能重置、调用廉价但连续性有限）与 open-agents 的实际架构特征吻合——**这不是巧合，是同一生态的设计共识**。被审计文件引用 open-agents 作为技能来源而非运行时依赖，进一步证实其"宿主无关"定位。

## 5. 定位总结

```
agents.md 生态栈（自下而上）：
  官方规范层    "README for agents"（项目事实，描述性）      ← 60k+ 项目
  ─────────────────────────────────────────────
  项目指南层    open-agents 自带 AGENTS.md（131行）          ← 单项目
  ─────────────────────────────────────────────
  行为宪法层    ★ 被审计文件（707行，跨项目，规范性）          ← 用户/组织级
  ─────────────────────────────────────────────
  宿主运行时层  Claude Code / Codex / open-agents…          ← 30+ 宿主
```

被审计文件填补的是**"项目指南层之上、宿主运行时层之下"的空位**：给任意宿主上的任意代理注入统一的行为纪律。这个空位在 2026 年的代理工程实践中正是各家（Anthropic 的 agent 指南、OpenAI 的 best practices、Vercel 的 open-agents docs）各自摸索、尚无标准答案的位置——本文件是一份**成熟度较高的独立答卷**，其独特卖点是证据纪律与反欺骗协议（08 §2 列举的增量设计）。

## 6. 遗留差距（与生态最佳实践相比）

1. **无提示注入防御**：上游生态已有 skillguard 类工具，本文件未要求使用；
2. **无宿主机制对接**：未利用 Claude Code hooks / Codex sandbox profile 等硬机制兜底 YOLO 自治；
3. **无版本与来源标注**：文件不含版本号、作者、变更记录（对照 PracticalSwan 技能的 front-matter 规范——name/version/last_updated——本文件自身未遵循其引用生态的元数据惯例），溯源只能靠内容指纹（本文档的 SHA-256 即为此提供锚点）。
