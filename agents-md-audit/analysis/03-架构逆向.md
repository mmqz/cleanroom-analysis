# 03 · 架构逆向：这份文件定义的软件是如何设计的

> 核心问题的完整回答。方法：把 707 行文本中的全部指令、伪代码块、触发条件当作"源代码"做逆向，重建出它所配置的目标系统。

## 0. 先纠正一个前提

**AGENTS-EN.md 不是软件本体，而是软件的"宪法层"。** 它不含一行机器码，无法独立运行；它的"解释器"是任何遵循 [agents.md 惯例](https://agents.md) 的 AI 代理宿主（Claude Code、OpenAI Codex CLI、Cursor、GitHub Copilot workspace、Vercel open-agents 等——§6 列出的技能目录 `.claude/` `.codex/` `.agents/` `.github/` 证实了多宿主兼容设计）。

因此"这个软件" = **宿主运行时 + 本文件注入的行为架构**。本文件定义了后者的全部，并假设了前者的存在。下面按六层重建。

## 2. 组件清单（16 个可辨识组件）

| # | 组件 | 文档依据 | 职责 |
|---|---|---|---|
| 1 | **代理内核/宪法** | 全文 | 定义身份、价值观与全部行为约束；本身即系统提示词 |
| 2 | **宿主运行时接口**（假设存在） | §6 "host agent"、§18 "sub-agent when available" | 提供 LLM、沙箱、工具、技能注册表；文档不定义它，只约定对它的期望 |
| 3 | **持久状态存储** | §2（8 类记忆文件） | 仓库文件系统 = 跨会话唯一记忆 |
| 4 | **真相优先级仲裁器** | §3（6 级） | 文档冲突时的裁判规则 |
| 5 | **会话恢复状态机** | §4（7 步） | 新会话/重置后从 git + 持久状态重建工作上下文 |
| 6 | **任务分类器** | §5（14 类） | 决定后续工作流形态与所需证据类型 |
| 7 | **技能发现与插件加载器** | §6（7 本地 + 7 外部源） | 找到并按契约加载可复用工作流 |
| 8 | **前端产品级工作流** | §7（7 步 + 反 AI 模式清单） | 前端任务专用管线，含浏览器渲染验证 |
| 9 | **实现完整性追踪器** | §8（7 层数据流） | 用户动作→UI→逻辑→数据→结果→错误态→加载态全链路检查，禁止"壳实现" |
| 10 | **比例规划器** | §11（8 字段模板） | Goal/Scope/Constraints/Facts/Unknowns/Approach/Acceptance/Verification |
| 11 | **YOLO 执行器** | §10（5 个暂停门） | 整阶段连续执行 + 有界自治 |
| 12 | **7 级验证流水线** | §17 | 从静态检查到真实用户路径的递进验证 |
| 13 | **独立审查子代理** | §18（9 项检查清单） | 实现者之外的"第二双眼睛" |
| 14 | **文档一致性契约系统** | §19 | 修改接口/命令/架构时同阶段同步文档，禁止第二真相源 |
| 15 | **Git 交付管道** | §20（3 阶段 6 命令） | 安全提交与远程同步 |
| 16 | **完成门 + 报告生成器** | §22（13 项）+ §23（7 节模板） | 完成度证据检查与标准化交付报告 |

另有两个横切子系统：**证据分级系统**（OBSERVED/INFERRED/UNKNOWN，§12）与**调试协议状态机**（Observe→Reproduce→Isolate→Hypothesis→Minimal change→Verify，§16）。

## 3. 数据流与控制流

### 3.1 一次任务的完整生命周期

```
用户请求
  │
  ▼
[分类器 §5] IMPLEMENTATION / BUG_FIX / ... （14选N）
  │
  ▼
[会话恢复 §4] git status → 读指令 → 读持久状态 → 查提交 → 查代码 → 验证完成度
  │            （不信任上一次会话的"声称"，只信任仓库证据）
  ▼
[技能发现 §6] 7目录 + 宿主注册表 + （必要时）7外部仓库
  │            选最小相关技能 → 读SKILL.md → 遵循其契约
  ▼
[研究 §12] 现有实现→行为→架构→约束→测试→上游issue→权衡→目标架构
  │          （重写/分析现有系统时强制先研究）
  ▼
[比例规划 §11] 8字段计划（拒绝为琐碎工作写巨大计划）
  │
  ▼
[YOLO执行 §10] ════════ 整阶段连续执行 ════════
  │   ║ 仅在5种情况暂停: 破坏性操作/需凭据/真歧义/范围必须变/危及无关工作
  ▼
[验证 §17] 静态→单元→集成→构建→真实进程→用户路径→回归
  │         （前端: 浏览器渲染验证；API: 打真实端点；持久化: 重启验证）
  ▼
[独立审查 §18] 派生子代理检查9类缺陷 → 修复 → 重新验证
  │
  ▼
[持久化 §2/§21] 把决策/约束/失败/证据写入 WORKLOG/TASKS → 更新文档契约 §19
  │
  ▼
[Git交付 §20] diff检查 → 只提交相关工作 → 验证后push（需证据）
  │
  ▼
[完成门 §22] 13项检查 → [最终报告 §23] Result/Changes/Skills/Verification/Review/Git/Status
```

### 3.2 状态迁移：记忆的读写时机

| 时机 | 读 | 写 |
|---|---|---|
| 会话开始 | §4: git状态、指令、任务状态、提交历史 | — |
| 工作中 | §3: 真相仲裁；§6: SKILL.md | §2: 发现重要事实即落盘 |
| 阶段结束 | — | §21: 更新阶段状态 → §19: 同步文档 → §20: 提交 |
| 环境重置 | 上述全部（设计目标：**任何代理可从仓库冷启动接管**） | — |

### 3.3 15 个休眠触发器（条件激活的子协议）

文档大量条款是"平时不生效、条件满足才激活"的休眠指令——这是它作为"操作系统"的关键特征，也是安全审计必须逐一定性的原因（定性结果见 04 文档）：

| 触发条件 | 激活的子协议 |
|---|---|
| 新会话/上下文重置 | §4 七步恢复 |
| 环境提供 Skills | §6 技能发现 |
| 本地无合适技能 | §6 转向 7 个外部仓库（**唯一供应链入口**） |
| 构建/大改前端 | §7 产品级前端工作流 |
| 无法完整实现 | §9 停在真实边界并报告（禁止伪装完成） |
| 阶段计划确立 | §10 YOLO 连续执行 |
| 分析/重写现有系统 | §12 先研究后动手 |
| Rust 代码引入 unsafe | §13 五项检查 + 最小边界 |
| 测试失败 | §16 六步调试协议 |
| 有意义的变更完成 | §18 独立审查 |
| 修改命令/API/架构/配置 | §19 同步持久文档 |
| 需要远程同步 | §20 验证后 push |
| 多阶段工作 | §21 维护阶段状态文件 |
| 即将宣布完成 | §22 十三项完成门 |
| 工作结束 | §23 固定模板报告 |

## 4. 设计哲学（7 条原则）

1. **仓库即唯一真相源**（Repository as the single source of truth）——对抗 §2/§21 明示的运行时特征："chat context、agent memory、sandbox、previous session may disappear at any time"。所有重要状态必须外化到文件系统，git 历史即完成度证据。
2. **证据优于断言**（Evidence beats assertion）——§1 的加粗原则，贯穿 §4（不信任上次的"完成"声称）、§17（[NOT VERIFIED] 强制标注）、§20（push 需证据）、§22（"勾选框不是证据"）。
3. **无壳原则**（No-shell principle）——§8/§9 双章禁止假实现：mock 数据、占位后端、断连 UI、假持久化、降级协议、假认证……共列举 16 种禁止形态。
4. **比例性**（Proportionality）——§11 拒绝大计划、§14 拒绝过度工程（7 类禁加抽象）、§15 拒绝假想风险的过度安全。最小可行架构。
5. **有界自治**（Bounded autonomy）——§10 是全文唯一的"放权"条款（YOLO），但用 5 个硬门反向约束；自治的边界恰好是破坏性与凭据。
6. **跨会话可续性**（Continuity across resets）——设计目标写死在 Final Rule："leave the repository in a state that another agent can inspect, run, verify, and continue without needing the previous conversation"。
7. **反 AI 生成物模式**（Anti-AI-pattern）——§7 明确列禁"任意紫蓝渐变、无意义玻璃卡片、hero+三卡片、假指标、不执行所宣传动作的按钮"；§13/§15 禁装饰性注释。这是针对 LLM 典型退化输出的"疫苗"。

## 5. 与生态的关系（交叉验证）

- 与 **vercel-labs/open-agents**（§6 引用的唯一代理框架）：其自带 AGENTS.md 是"单项目工程指南"（认证/数据库/命令/代码风格），被审计文件是"跨项目行为宪法"，仅共享惯例格式，无文本派生关系（共同行均为短语）。二者构成惯例的两个层级：项目级 AGENTS.md ← 用户/组织级 AGENTS.md（本文件）。
- open-agents 的实际工具层（`packages/agent/tools/`: bash/read/write/glob/grep/skill/task/todo/fetch + path-security）恰好就是本文件 Layer 0 假设的能力面；其"agent 不在沙箱内运行、通过工具交互"的三层架构（Web→Agent→Sandbox）与本文件的 Layer 0/2 假设完全兼容。
- 本文件同时是 **Claude Code 的 CLAUDE.md 惯例、OpenAI Codex 的 AGENTS.md 标准、以及 skills.sh 技能生态**（7 个外部仓库中 4 个出现在 agentskills.io 注册表中）的超集强化版。

## 6. 设计评注：这份宪法的高明与代价

**高明之处**：
- 把"运行环境不可靠"（模型重置、沙箱回收、廉价但无连续性的调用）当作**一等设计约束**，整个状态子系统都是为它服务的——这是对 serverless/无状态计算架构思想的移植；
- 用提示词首尾重申（Purpose + Final Rule）巩固关键约束，用伪代码块降低 LLM 误读率——作者精通 LLM 行为工程；
- 反欺骗条款（"Never claim a push succeeded without actual evidence"、"A checked box without evidence is not evidence"）是在**约束代理的自我报告诚实性**，这在同类文档中罕见。

**代价/风险面**：
- §10 YOLO 是人工监督的系统性削弱，其安全性完全依赖 5 个暂停门的语义被宿主 LLM 稳定遵守——而这是概率性的，不是机制性的；
- §6 外部仓库引用是活的供应链（上游内容可变），文档的缓解措施（"inspect and adapt only what is relevant; do not blindly install"）同样只是语义约束；
- 整部宪法**没有任何针对提示注入的防御条款**（讽刺的是，PracticalSwan 仓库自带的 skillguard 技能反而提供了这种防御——本文件引用了它却没要求使用它）。
