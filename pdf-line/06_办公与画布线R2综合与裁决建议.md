### 1.2 三问（D1 三问逐条给建议；终裁留用户裁决）

**问① MD/办公/画布三线是否统一协同内核？**

【建议】统一，且统一在 CRDT 侧——以 Yjs 同步协议子集作为跨线协同语言，
按线分层实现强度。依据三判据（collab-a §6.3）：

1. 格式保真耦合度（第一判据）：MD 线（mdcore 自有树模型）与画布线（元素
   模型/图模型）均为自有 schema，与 CRDT 的「文档模型自定、协议无关格式」
   完全解耦；OT 路线与私有二进制真相源/OOXML 装配深绑（office-b §4/§5
   实证），自研复刻该绑定成本高且与 op-first 树结构相斥（collab-a §6.3
   判据 1，引 office-a §13-3「快照即模型是反面教材」）。
2. 离线/断线需求（第二判据）：工作台 local-first 定位，Yjs 离线合并免协议
   （collab-a §3）；OT 需自建版本对齐协议（Univer 18 类 WS 事件 +
   sid/reqId 全套、ONLYOFFICE auth 补拉——office-a §5 / office-b §3）；
   mdcore 既有 sync_resync/revision 体系可与 CRDT 叠加（collab-a §6.3）。
3. agent 写入通道（第三判据）：Yjs 官方威胁模型的「untrusted 走 fork 文档 +
   可信端审核合并」与「agent 走同一 op 通道」互证（collab-a §4.6 ×
   office-a §13-8；Univer Pro 的 DirectWrite/ForkUnit 语义兼容——office-a §7）。

诚实登记的反对/谨慎因素（collab-a §6.3 判据 4，原文三条）：
① map/属性并发在 CRDT 侧退化为 LWW、删除零元数据——意图审计/归因需产品层
外挂；② Yjs 内核处 v13/v14 断代——直接依赖库本体有代际风险，缓解 = 只依赖
其冻结协议或选 yrs/自研；③ 中心化部署下 OT 的服务端管控更直接——若需强
仲裁（企业审计）需在 CRDT 之上再叠仲裁层，复杂度未必更低。

**问② 若统一，实现层选型排序？**

【建议】排序：**(a) yrs（Rust，Yjs 协议兼容）起步 → (b) 净室自研 YATA 内核
对齐协议 → (c) Univer 式自研 changeset（仅当办公线保真需求压倒一切时作特例
通道）**。理由：协议层采纳 Yjs 同步协议子集（SyncStep1/2/Update + SV +
awareness 编码，全 MIT、协议十年冻结且已 RFC2119 文档化——collab-a §4.2/
§6.3）；实现层三选一的口径与初步依据在 collab-a §6.3 已给出，其中 (a) 与
mdcore「引擎化 + 外置能力」路线最契合（collab-a §6.3）。(c) 通道仅保留为
表格域保真的特例出口，不作为三线通用底座。【建议】yrs 评估 pass 列为最优
先后续轮（§8.2），其结论直接决定 (a) 与 (b) 的取舍。

**问③ 中心化仲裁与离线合并的取舍？**

【建议】双层结构：**「中心化权威快照 + 客户端 CRDT 离线自愈」**——

- 服务端层：权威快照/checkpoint + 幂等保存（快照+oplog 混合稳态——
  collab-a §6.1；Univer 版本骨架 baseRev/revision+(sid,reqId)+(from,to]
  补拉 + checkpoint 幂等照抄——office-a §13-7）。
- 客户端层：CRDT 免协议离线自愈（任意顺序、任意缺口的 update 先收下后
  整合——collab-a §2.3/§3）。
- agent/不可信写入：fork 文档 + 审核后合并（collab-a §4.6），与
  DirectWrite/ForkUnit 范式（office-a §7）同构，即「agent 不做旁路改文件，
  走同一通道 + 幂等命令 + 审计」（office-a §13-8）。
- 代价登记：企业级强仲裁需在 CRDT 之上叠仲裁层（collab-a §6.3 判据 4-③）；
  审计/归因需产品层外挂记账（collab-a §1.6 取舍画像）。

### 2.4 横贯结论

（penpot-a §1.3/§5-2）。

## 3. 双态决策（D2，留用户裁决）

### 3.1 AFFiNE「两视图投影」模式要点（affine-a）

- **双态映射本质 = 单一 block 树 + 双视图层换装**：画布几何（xywh）、
  z 序（fractional index 字符串）、双态可见性（displayMode 三态
  DocAndEdgeless/DocOnly/EdgelessOnly）都是 block model 的普通 props；
  doc 模式不消费的字段命名空间化挂在 edgeless 子对象下（affine-a §1.1）。
- **纯图形不占 block 节点**：收进专用 surface block 装箱的 Y.Map（affine-a §1.1）。
- **edgeless 视图复用 doc 渲染**：toGfxBlockComponent(DocComponent)
  继承/包装，画布上的文档卡片与文档模式像素级同源；CSS transform 定位
  （affine-a §1.2）。
- **切换四层状态保持**：模式值两级（primaryMode 持久偏好 / editorMode
  当前会话）；整组件换装数据零迁移；视口与滚动按态分槽持久化；undo 历史

## 6. 安全面合成

### 6.1 三大敌意输出裁决 → dsh 管线层消毒三闸

依据全部为 office-d 重做轮修补版结论：

1. **CSV 公式首字符（= + - @）消毒四库零实现**：能产 CSV 的两家均无消毒
   （exceljs 无消毒、quoting 只防语法歧义；sheetjs 反而主动以 `=` 前缀
   重建公式文本——公式注入是特性而非被防的面）（office-d §5.1）。
2. **XML 控制字符面三档实况**：损坏档（docx/pptxgenjs——非法控制字符
   原样透传，产出非法 XML，Word/Excel 拒开，管线可靠性故障面）；剥除档
   （exceljs——xmlEncode 静默剥除非法集+0x7F，产出合法 XML 但静默丢字符，
   保真故障面）；保字符档（sheetjs——_xHHHH_ 转义，四库唯一达标）（office-d §5.2）。
3. **docx 域指令无白名单直通**：SimpleField 任意指令零校验写入 w:instr
   （INCLUDETEXT/DDE 等危险域可由 LLM 输出注入）；内建域面为结构化构造、
   面受限（office-d §5.3）。

【建议】dsh 生成态出口三闸（消毒 = dsh 管线层责任，office-d §8-2）：

- **闸一 字符过滤器（喂入前）**：走 docx/pptxgenjs 路线防拒开级损坏；走
  exceljs 路线防静默丢字符——一处统一做，勿信库；xlsx 路线若走 sheetjs
  可复用其转义层（office-d §5.2 裁决 2）。
- **闸二 CSV 首字符消毒（出口处）**：对 CSV/TSV 出口做首字符改写（前置
  `'` 或空格，或按目标应用策略拒写）；xlsx 路线不必消毒首字符（注入只在
  CSV/TSV 粘贴与打开时发生）（office-d §5.1 裁决 2）。
- **闸三 域白名单（docx 面向 LLM 时）**：建议白名单 DATE/PAGE/NUMPAGES/
  TOC/PAGEREF/MERGEFIELD/SEQ；黑名单首列 INCLUDETEXT/INCLUDEPICTURE/DDE
  （office-d §5.3 裁决）。

附加登记：sheetjs HTML 出口超链接 href 未转义（敌意面），面向浏览器需
自建转义层（office-d §5.1）；pptxgenjs 属性位（objectName 等）存在属性
注入缺口，需调用方兜底（office-d §5.2）。
