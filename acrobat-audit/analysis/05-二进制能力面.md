# 05 · 二进制能力面：MSI 内嵌 36 个 PE 的深度审计

> 轮次：第 5 轮（R1 数据库逆向 → R2 安装行为面 → R3 网络遥测面 → **R5 二进制能力面**）
> 对象：`AcroPro.msi`（26.002.21931）Binary 表承载的 36 个 PE 流
> 工具：`tools/msi_pe_audit.py`（可复现，仓库内直接运行）
> 证据：`evidence/pe-capability/pe_capabilities.json`（全量）、`capability_matrix.json`（矩阵）、`strings_hits.json`（字符串）

## 1. 为什么需要这一轮

前四轮的证据链止步于"表级"：MSI 数据库告诉我们**哪些组件会被写入**（Registry 3306 行、ServiceInstall、Run 键、CA 336 行），但没有回答**执行体本身具备什么能力**。R1 只完成了 PE 的身份识别（版本块），二进制内容从未打开。本轮把证据链从表级钻到字节级——逐一解析 36 个 PE 的导入表、导出表、节区熵、时间戳与字符串，回答：

1. 安装器二进制层有没有**网络外联能力**（R3 只证明了字符串层无端点）？
2. 有没有**进程注入**（WriteProcessMemory / CreateRemoteThread / SetWindowsHookEx）？
3. 12 个写注册表的 PE，写的**自启动路径**是什么？
4. 两个无版本信息的 EXE 到底是谁（R1 遗留问题）？

**两个遗留未知数的落定证据**：

- **s030 = BlockEntryPoints**：宽字符串含日志名 `AcroInstEntryPointBlock.log`；创建互斥体 `Global\Acro Update Mutex` 与命名管道 `\\.\pipe\{32B6B37A-4A7D-4e00-95F2-6F0BF3DE3E00}`；`[IsMsiBusy]` 探测 MSIServer 服务状态防并发安装；SDDL `S:(ML;;NW;;;LW)` 给管道打了低完整性标签（防御性设计）。
- **s033 = ExecuteInst_Cmd**：PDB 路径铁证 `D:\DCB\CBT_Main\Acrobat\Installers\ExecuteInst_Cmd\Release_x64\ExecuteInst_Cmd.pdb`（泄露 Adobe 构建树结构）；命令行证据 `msiexec.exe /i %s REINSTALLMODE=omus REINSTALL=ALL IS_SEC_INSTALL=1 %s`（二级安装链）与 `cmd /c del "%s"` + `ComSpec`（临时文件清理）。

**构建卫生发现**：s023（606 KB、60 个导出的安装引擎主力）的版本块是坏的——`InternalName=ADelRCP`、`ProductName=NoFeatureError`、`ProductVersion=Failed to identify track of installing product`。这是 Adobe 构建系统把陈旧版本块编译进产物的卫生缺陷（R1 的两处身份误判即源于此），非恶意特征。

## 3. 能力矩阵（导入表判定）

| 能力 | 命中数 | 归属 | 复核结论 |
|---|---|---|---|
| proc_inject（WriteProcessMemory / CreateRemoteThread / SetWindowsHookEx 等） | **0/36** | — | **全载荷零注入 API** |
| 网络导入（wininet / winhttp / ws2_32 / urlmon / winsock） | **0/36** | — | **全载荷零网络外联能力** |
| proc_exec | 12 | ANCUtili, AbcpyDll, ADelRCP, Adobeisf, AcroSup64, AcroTgts, ExecuteInst_Cmd, ISRegSvr, InstPDFM, InstUtil, PrintInf, SetAllUsers | 命令面 = `msiexec`（二级安装）/ `rundll32`（CA 自调用）/ `regsvr32`（COM 注册）/ `cmd /c del`（临时清理）——全部安装器标准机制 |
| proc_enum | 3 | ADelRCP, InstUtil, SetAllUsers | 对应导出 `KillProcess*` `CloseApplications`——安装前关闭正在运行的 Acrobat 进程以释放文件句柄 |
| reg_write | 12 | （见上表主力 CA） | 写入面与 R2 Registry 表 3306 行吻合；唯一自启动写入 = `Run\Acrobat Assistant 8.0 = "[DISTILLR]Acrotray.exe"` |
| service_ctl | 6 | ADelRCP, ArmInst, Adobeisf, BlockEntryPoints, ExecuteInst_Cmd, InstUtil | 与 R2 ServiceInstall/ServiceControl 闭环：装 `AdobeARMservice`（ArmInst），卸载时删（ADelRCP 字符串 `AdobeARMservice` 佐证） |
| com_schtasks（CoCreateInstance 族） | 6 | ANCUtili, ADelRCP, ArmInst, ISRegSvr, PerfInst, SetAllUsers | 计划任务创建者 = ArmInst（导出 `AddTask`/`RemoveTask` + 字符串 `Adobe Acrobat Update Task`），与 R2 一致；字符串层**无** Task Scheduler COM CLSID `{0F87369F-…}` 硬编码 |
| privilege（AdjustTokenPrivileges） | 4 | ADelRCP, AcroTgts, InstPDFM, InstUtil | 安装期 ACL/令牌调整（写 Program Files / HKLM 所需） |
| crypto | 1 | ADelRCP：`CryptAcquireContextW` + `CryptHashData` | **仅哈希，无加密/解密函数**——缓存清单或文件完整性校验用途 |
| debug_anti | 19 | — | `IsDebuggerPresent`/`GetTickCount`/`QueryPerformanceCounter` 属 CRT/性能计数常态，无反分析组合证据 |
| screen / cred / hook_kb / wer | 0 | — | 无截屏、凭据读取、键盘钩子、WER 注册 API |

节区熵全部 < 7.2（无加壳/无混淆载荷）；`TsnIorcAeBoda`（= `AdobeAcroInst` 变序）等字符串倒置属安装同步对象的轻量防碰撞命名，非隐蔽信道。

## 4. 字符串层网络面（与 R3 闭环）

36 个 PE 的全部 URL 命中只有三类，**无一 Adobe 域**：

1. **DigiCert/VeriSign/Thawne CRL·OCSP URL**（证书链内嵌产物，19 个签名 PE 均有）；
2. `https://clients2.google.com/service/update2/crx`（仅 ADelRCP s023）——注册表交叉定位到落点：`HKLM\SOFTWARE\Google\Chrome\Extensions\[CHROME_EXT_ID]` 的 `update_url` 值，即 Chrome 扩展离线注册的标准更新通道；同组件还写 `SOFTWARE\Google\Chrome\NativeMessagingHosts\com.adobe.acrobat.chrome_webcapture`（Chrome 原生消息桥）。这是扩展注册机制，非遥测；
3. `http://www.flexerasoftware.com`（Flexera 版权串）。

**结论与 R3 闭环**：安装器静态载荷（Property 表 + 36 PE 字符串 + 36 PE 导入表）三层全部证明——**安装期唯一网络通道就是 ARM 自更新（armmf.adobe.com，R2/R3 已定级），不存在隐藏的遥测外联能力**。运行期遥测面（Acrobat 主程序、AGS）不在安装器载荷内，属 R6 范围。

## 6. 风险增量判定

| 检查项 | 结果 |
|---|---|
| 休眠触发器（条件激活的恶意逻辑） | **零**：CA 触发条件全部在 R2 InstallExecuteSequence/CA 表中枚举完毕，二进制层无隐藏网络/注入能力可供触发 |
| 进程注入 | 零 API |
| 网络外联 | 零导入、零 Adobe 域字符串 |
| 自删除闪避 | `cmd /c del "%s"` 指向临时解包文件清理（ComSpec 模式），非自身删除 |
| 提权滥用 | AdjustTokenPrivileges 仅 4 个安装期 CA，无运行期驻留体 |
| 加壳/混淆 | 零（熵全部 < 7.2） |
| 无签名二进制 | 17 个 _IsIcoRes 无内嵌签名，但 MSI 整体已被 R0 验签（authentihash 匹配），流内容受容器签名保护 |

**本轮风险定级：安装器二进制层 = 低（与 R1–R3 结论互相加强，证据链闭合）**。

新发现中值得用户知悉的两点（均非安全威胁，属知情权）：① 默认安装会注册 **Chrome 扩展 + Chrome 原生消息宿主**（`com.adobe.acrobat.chrome_webcapture`），浏览器集成面比通常认知的宽；② Adobe 构建管线存在**坏版本块**卫生问题（s023），使第三方工具的组件识别产生偏差。

## 7. 下一轮（R6）预告

安装器侧证据链已四层闭环（数据库 → 行为 → 网络 → 二进制）。R6 转向**运行期引入面**：AGS（AdobeGClient.exe，Adobe Genuine Service）官方分发包取证——验证其签名链、逆向其服务/计划任务/网络端点，直击最初会话发现的 CPU 异常与"侵入式遥测"感知的根因。
