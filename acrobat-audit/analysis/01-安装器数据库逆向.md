# 01 · 安装器数据库逆向：从混淆流名到 11 张表全量重建

> 对象：`source/AcroPro.msi`（SHA-256 `089dc9a2…60f4b2d`，Adobe 官方 Acrobat Pro DC 26.002.21931 分发链中的基础 MSI，构建于 2021-02-01，由 2026-09 的 .msp 增量升级到当前版本）
> 前置：本仓库 Task 1（见主 worklog）已验证下载链路与 Authenticode 签名链完整，本篇回答下一个问题——**这个签名合法的安装器，安装时到底会对系统做什么**。
> 方法：纯 Python（olefile + struct + strings）逆向 MSI 数据库物理格式，不依赖任何 Windows 专有工具。

## 1. 为什么需要逆向：工具链的缺失与流名的反常

标准做法是用 `msitools`（msidump/msiextract）或 WiX/DTF 解包 MSI。本审计环境为 Linux 容器，无 sudo 权限、无 msitools、无 7-zip，可用工具仅有 Python 3.13、olefile（pip 安装）和 binutils `strings`。这反而促成了一次彻底的格式级取证——不依赖工具的黑盒行为，每一个字节的结构都经过显式验证。

用 olefile 枚举 OLE 复合文档得到 **138 个流、13,050,541 字节**，立即出现两个反常：

1. **没有任何一个标准系统流名**。正常 MSI 应当有 `!_StringPool` / `!_StringData`，以及 `Property`、`File`、`CustomAction` 等明文表名流。本文件全部 138 个流名均为形如 `䌋䄱䜵㪾…`（U+3xxx–U+4xxx CJK 区位）的混淆名——这是 InstallShield 2012 Spring（OLE 元数据 `creating_application: InstallShield® 2012 Spring - Professional Edition 19`）对数据库流名实施的确定性重编码，用于规避脚本化解包。实验证明该编码非池索引映射（将流名单元当作字符串池索引解码得到的是无关内容），亦非简单仿射变换（'D'/'P' 同位差 0x300 ⇒ 斜率 64，但位置 0 上族间差 0x179 不能被 64 整除，假设被数据否证）。
2. **36 个 PE 流裸存在**。魔数 `MZ` 的流有 36 个，另有 BMP×3、JPEG×1。它们不是压缩在 CAB 内，而是以未压缩流形式直接存放在 OLE 复合文档中——即 MSI **Binary 表**的载荷（定制动作 DLL 与安装 UI 资源），这是后续行为分析的直接物证。

结论：流名不可读，则**表的身份必须由内容判定**——这正是本篇的方法论主线。

## 2. 字符串池：一个被数值检验锁死的格式

流 `#067`（781,290 字节）在前 4096 字节上可打印率 100%，内容为 MSI 模式验证描述串（"Number that determines the sort order…"），且**全文不含任何 NUL 分隔符**。这确认它是 StringData（所有持久字符串首尾相接），同时意味着切分边界必须来自配套的 StringPool。

流 `#068`（117,716 字节）与 #67 共享 4 个混淆名单元前缀，形似一对系统流。对 117,716 = 4 × 29,429 做三种格式假设检验：

| 假设 | 结构 | 数值检验 | 结果 |
|---|---|---|---|
| A | `u32` 长度数组 | Σ = 5,434,239,978 ≠ 781,290 | ✗ |
| B | `(u16 长度, u16 引用计数)` | **Σ长度 = 781,290，与 StringData 逐字节相等** | ✓ |
| C | `(u16 引用计数, u16 长度)` | Σ = 82,908 | ✗ |

假设 B 通过唯一的闭合数值检验：**29,429 条字符串、每条 4 字节池记录（u16 长度 + u16 引用计数）、累计长度与 StringData 完全一致**。引用计数值域（1–383）也符合"高频字符串被多表共享"的预期。切分后抽样：`[1]='Name' [2]='Table' [100]='Class'`、`[3909]='PDFMaker_Ofc_PDFMVisio.vsl'`、`[22996]='SOFTWARE\Adobe\Acrobat\Exe'`——池内容自洽。

## 3. 表流的物理格式：列块布局

对候选表流做 u16 细胞解码后，结构在多张表上交叉成立（这是本审计最关键的格式发现）：

- **列块（column-major）布局**：流 = `[第1列全部行][第2列全部行]…`，而非行优先。例如 Property 表 626 细胞 = 313 行 × 2 列：细胞 0–312 全部是属性名，313–625 全部是值。
- **字符串细胞** = `u16` 字符串池索引；`0` = NULL。
- **整数细胞** = `u16` 且高位置位（`0x8000 | 值`）；`0x8000` 即整数值 0。InstallExecuteSequence 的序号列（如 `0x88FC` → 2300）与 ServiceControl 的事件位列（2/34/48/51/128）在该解释下全部落入 MSI 语义的合法值域。

用该格式在内容特征上锁定 11 张表并全量重建（`evidence/msi-tables/`）：

| 表 | 流# | 规模 | 内容判据（证据） |
|---|---|---|---|
| `_Tables` | 069 | 78 行 | 78 个表名，含全部标准表名 + InstallShield 私有表 |
| `Property` | 128 | 313 行 | `UpgradeCode={AC76BA86-0000-0000-7760-…}`（Acrobat 家族 GUID） |
| `CustomAction` | 133 | 336 行 | 动作名与 Binary 键/入口点对齐 |
| `InstallExecuteSequence` | 105 | 252 行 | 标准动作名 + Adobe 定制动作 + 条件 + 序号 |
| `Binary` | 097 | 39 行 | 39 键与 36 PE + 3 图像流一一对应 |
| `ServiceControl` | 091 | 7 行 | `AdobeARMservice/stisvc/Spooler/wsearch` |
| `ServiceInstall` | 092 | 16 细胞 | `AdobeARMservice`（详见 02 篇） |
| `Media` | 085 | 6 行 | `Core/Intermediate/Extras/Optional/AlfSdPack/Languages.cab` |
| `Directory` | 098 | 806 行 | `ProgramFilesFolder/TARGETDIR/…` 目录树 |
| `Component` | 109 | 2,308 行 | 组件键与 File/Registry 外键闭合 |
| `Registry` | 088 | 3,306 行 | 3,306 条注册表写入（见 02 篇过滤） |
| `File` | 131 | 5,280 行 | 8.3 短名\|长名 格式的落盘清单 |

**诚实记录已知局限**：CustomAction 与 File 两个流存在列块内的异质段（CustomAction 的 Type 块前段为整数、后段出现 80 个连续 `ADelRCP` 字符串引用；File 表列语义有整体错位），提示 InstallShield 对含变长/流引用列（v0 类型）的表使用了额外的内联编码。因此这两张表的**逐行对齐不完美**，但聚合统计（动作数、Type 分布、Source 分布、文件名清单）取自完整连续段，证据强度不受影响；分析篇中凡引用此二表之处均已标注。

## 4. Binary 表 39 键与 36 个 PE 的身份

通过 PE 版本资源（`strings -el` 提取 VS_VERSIONINFO）识别全部 PE 流：

| Binary 键（MSI 内） | PE 身份 | 角色 |
|---|---|---|
| ADelRCP | ADelRCP.dll（21.1.20135）×2 | **注册表清理引擎，承载 80 个定制动作** |
| AbcpyDll | AbcpyDll.dll | **ABCPY.INI 部署配置引擎**（OEM/静默安装参数） |
| ArmCustomActions.dll / ArmInst | ArmInst.dll (1.824.42.0176) | **ARM 更新服务安装器**（服务+计划任务） |

| AcroSup64 | AcroSup64.dll | 64 位安装支持 |
| AcroTgts | AcroTgts.dll | 升级目标检测（旧版本清理矩阵） |
| ANCUtility | ANCUtili.dll | Acrobat 新式组件工具 |
| InstUtil / InstOOBELib / InstPDFM | 同名 DLL | 通用安装/OOBE/PDFMaker 安装 |
| PrintInf / PerfInst | 同名 DLL | 打印机 INF / 性能计数器安装 |

交叉校验：`ISSELFREG.DLL`、`SetAllUsers.dll`、`Kernel`（"InstallShield (R) 64-bit Setup Engine"）的 Flexera 签名与 OLE 元数据中的"InstallShield 2012 Spring"一致；17 份 _IsIcoRes.exe 与 `setup.ini` 的 26 语言清单数量级吻合（部分语言共用图标）。

## 5. 可复现性

`tools/msi_audit.py` 将上述全部步骤整合为单一管线（提取→池解码→表重建→行为汇总→PE 挖掘），在仓库内执行：

```
$ python3 tools/msi_audit.py
[init] MSI SHA-256 = 089dc9a2…
[extract] 138 流; 分类: {'bin': 95, 'PE': 36, 'JPEG': 1, 'BMP': 3, 'ASCII': 3}
[tables] 字符串池: 29429 条, 781,290 字节
[tables] 重建 11 张表
[behavior] CA=336 IES=252 Registry=3306 Binary=39 自启动命中=30
[strings] 挖掘 36 个PE流
```

复现一致性验证：11 张表中 10 张与 `evidence/msi-tables/` 的初次导出**字节级一致**（Binary.json 因新管线补全 Data 列而结构增强，属预期差异）。

本篇产出回答了"这个安装器由什么构成"：一个 InstallShield 2012 骨架 + 336 个定制动作 + 39 个 Binary 载荷 + 3,306 条注册表写入 + 5,280 个文件、由 6 个外部 CAB 承载落盘内容的多语言安装数据库。**它把什么写入系统、何时写入、向谁报告**——见 02、03 篇。
